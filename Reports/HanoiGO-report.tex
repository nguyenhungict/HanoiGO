\section{Context}

An increasing number of people travel abroad each year, and many of them use mobile phones or websites to plan their trips. According to Gretzel et al. \cite{gretzel2015smart}, using digital tools such as online maps and mobile apps can help tourists have a better travel experience. However, for foreign visitors who come to a large, densely visited city like Hanoi \cite{vietnamtourism2024}, planning a trip on their own is often not easy, especially if they travel alone.

There are already some well-known travel apps like Google Maps, TripAdvisor, or Booking.com. However, these apps usually only help with finding directions between two places. They are not built for planning a full trip across many days or for finding key information like place opening hours, local cultural tips, or descriptions in English. Because this kind of information is often scattered across many websites and blog posts, tourists often spend considerable time searching for it independently \cite{buhalis2020smartness}.

In addition, solo travelers often face difficulty finding other people to travel with, or sharing costs like taxi fares \cite{buhalis2019cocreation}. Most general social apps do not have a map feature, so it is hard to see if any group activity is happening nearby in real time. These issues make solo travel in Hanoi more difficult than necessary. There is a clear need for a focused tool that integrates maps, trip planning, and social features in a single platform.

Because of this, I decided to build HanoiGO, a web application designed for foreign tourists visiting Hanoi. It helps users plan their daily trips automatically and connect with other travelers nearby on a shared map.

\section{Motivation}

The decision to undertake this project is driven by both practical travel navigation needs and technical aspirations.

First, I want to help tourists plan their trips more easily. I noticed that it is hard to arrange a list of tourist spots into a clear schedule across multiple days, especially because some places in Hanoi have specific opening hours or close for lunch. To solve this, I designed a multi-day scheduling method. It first groups tourist spots into daily clusters using K-Means clustering, and then finds a convenient order to visit places on each day that respects opening hours and the daily time limit. This scheduling method uses real-time travel times from the Goong Maps API to minimize waiting and travel time.

Second, I want to build a map-based feature that helps solo travelers meet other people. On most social networks, travel plans are shared only as text or photos, and there is no way to see where people are on a map. HanoiGO gives users a way to create and join group activities that are shown as dynamic markers on a live map. These markers change color and flash based on the activity's time status. When a user finds an interesting group activity, they can also copy the linked travel plan directly into their own account with a single click. This is done through a deep copy transaction in the database, which replicates all trip days and stops, and is much faster than re-creating the plan manually.

From a technical side, this project is also a chance for me to learn and practice useful development skills. I used Next.js and TypeScript to build a responsive user interface, NestJS to build the backend server with a modular structure, PostgreSQL with PostGIS to store and query spatial location data, and WebSocket connections for real-time group chat.

With these motivations in mind, I established clear objectives to guide the development process.

\section{Objectives}

The main goal of this project is to build a complete web application that helps foreign tourists in Hanoi plan their trips and connect with other travelers more easily. To reach this goal, I have set a list of both functional and technical objectives.

In terms of features, I aim to do the following. First, I want to build a secure account system with email-based OTP verification so that only real users can access the platform. Second, I want to build a multi-day trip planner that automatically groups and sequences tourist spots into convenient daily plans using clustering and sequencing methods, taking into account real travel times, opening hours, and lunch breaks. Third, I aim to add a live map with dynamic status markers and a WebSocket-based group chat so travelers can easily find and communicate with other people nearby. Fourth, I plan to create a shared feed page with quick cloning features, allowing users to view, like, comment on, and instantly copy complete multi-day travel plans into their own account.

On the technical side, my goals are as follows. First, I will build a secure authentication system using stateless JWT tokens stored in HttpOnly cookies to protect against XSS attacks, combined with a token version field on each user account to allow token invalidation when needed. Second, I will use NestJS for the backend and Next.js for the frontend to create a clear and well-organized application. Third, I will use PostgreSQL with PostGIS extensions to store spatial location data and perform proximity queries efficiently. Fourth, I will implement real-time group messaging using WebSocket connections so that members of the same activity can communicate instantly in a shared chat room. Lastly, I will test and improve the scheduling algorithm to make sure it produces correct and useful results for a web application.

By reaching these goals, I hope to build something useful for foreign tourists in Hanoi and also show that I can apply modern web development skills in a real-world project.

\section{Overview}

This chapter explains how the system works internally, showing the main features, the key modules, and how different components interact with each other. It describes how the ideas introduced in Chapter I are turned into a working web application.
 
HanoiGO is designed for two types of users: Tourists and Administrators. Tourists use the platform to explore places in Hanoi, generate daily trip schedules automatically, and join group activities on a live map. Administrators manage user accounts and keep the platform running smoothly through a dedicated management panel.
 
The backend is developed with NestJS, and the frontend is built with Next.js. Location data is stored and queried using PostgreSQL with the PostGIS extension. Real-time group chat is handled through WebSocket connections using Socket.io. This architecture helps the system manage different types of data efficiently and respond quickly to user actions.

Figure~\ref{fig:seq_plan_trip} shows how the system generates and saves a multi-day trip plan. The user selects places on the map and sets trip parameters such as the number of days, travel date, and start and end times. The backend fetches the selected places, removes closed ones, groups them into daily clusters using \texttt{K-Means}, and calls the \texttt{Goong Maps API} to get travel times. An exact (brute-force) time-window search builds each day's route for small days, with a Greedy Nearest Neighbor heuristic kept as a fallback for larger ones; dropped places are re-inserted where possible using the cached travel-time matrix, and each day is then re-confirmed using the same exact search for small days. When the user confirms the result, the frontend saves the full trip structure to the database.

\section{System Architecture}

This section presents the system architecture to give an overview of how the HanoiGO platform is structured. Figure~\ref{fig:sys_arch} presents the system architecture of HanoiGO, which is designed in a client--server model. The system includes four main components: Client Layer, Core Backend, Data Layer, and External Services.

\begin{figure}[H]
    \centering
    \makebox[\textwidth][c]{\includegraphics[width=1.25\textwidth]{sys-arc.pdf}}
    \caption{HanoiGO System Architecture Diagram}
    \label{fig:sys_arch}

The Client Layer is the web interface used by travelers. It is built with Next.js and TypeScript to provide type safety and a consistent development structure. This layer communicates with the backend using HTTP for normal actions and WebSocket for real-time features such as group chat and notifications.

The Core Backend is responsible for handling the main functions of the system. It manages user authentication using JWT and Passport. The backend includes several modules, such as user management, admin functions, trip planning, activities, and notification handling. Prisma ORM is used to interact with the database, while Socket.io supports real-time communication.

The Data Layer stores system data using PostgreSQL. PostgreSQL with the PostGIS extension is used for structured data, geographical information, and spatial queries. Redis is also configured in the environment to support future chat scaling. 
The External Services component includes third-party services that support the platform. The Goong Maps API is used to calculate travel times and distance matrices. SMTP via Gmail is used for sending verification emails, while Supabase Storage handles uploaded media files.

\section{Tools and Techniques}

This section describes the main development tools and approaches used to build the platform.

\subsection{Development Tools}

Visual Studio Code was used as the main code editor for its TypeScript support. Git with GitHub managed version control, and pull requests were reviewed before merging. Docker ran the PostgreSQL and Redis services in containers to keep the setup consistent across machines. For the database, Prisma defined the schema and managed migrations, generating the matching SQL commands automatically when the schema changed.

\subsection{Frontend Techniques}

The frontend is built with Next.js, using the App Router to manage routes and loading states. It separates Server Components, rendered on the server, from Client Components that handle user interactions, which helps pages load faster. The Socket.io Client connects to the backend over WebSockets for real-time group chat and notifications, while React Hooks (including custom hooks for authentication and socket management) handle component state. The interface uses Tailwind CSS so it adapts to different screen sizes, from desktops to smartphones.

\subsection{Backend Techniques}

The backend is built with NestJS, which organizes code into modules such as authentication, group chat, and trip planning. Each module has controllers for incoming requests and services for the business logic. Real-time features use NestJS WebSocket gateways, which verify the JWT token on connection and place users into rooms by activity ID so messages reach only the correct members. File uploads use Multer middleware, which limits uploads to image files up to 10MB and stores them in Supabase Storage with a local storage fallback.

\section{Backend Development}
\subsection{Authentication}

The system used JSON Web Tokens (JWT) to manage user identity and access control. Upon a successful login, an access token and a refresh token containing the user's ID, username, and role (USER or ADMIN) are generated. For security purposes, these tokens are digitally signed and valid for 7 days. They are primarily stored in browser cookies (via HttpOnly cookies), with a backup in the authorization headers for WebSocket stability. While public routes like registration are accessible to all, private features such as Group Chat and Trip Planning are protected by JWT authentication, and administrator endpoints are further restricted through role-based access control (RBAC).

To ensure data integrity, passwords are hashed using bcrypt before storage, making them irreversible even if the database is compromised. \subsection{Trip Planner}

The trip planner is the core feature of HanoiGO. It builds convenient multi-day itineraries from a set of selected places, the number of travel days, and the daily start and end times. The planner handles both spatial data (where the places are) and temporal constraints (opening hours, lunch breaks, and the daily time limit). 

To solve this problem efficiently for a web application, the system uses a multi-stage pipeline: fast heuristics first assign places to days, and an exact search then orders the places within each day. The sequence of these planning stages is illustrated in Figure~\ref{fig:trip_pipeline}. The process consists of six sequential steps:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.65\linewidth]{trip-pipeline.png}
    \caption{The multi-stage trip planning pipeline of HanoiGO}
    \label{fig:trip_pipeline}
\end{figure} 

\textbf{Step 1: Pre-Filtering} 
\\ The system first checks the selected places against the user's travel dates. Any place that is closed on all days of the trip is filtered out. This pre-filtering step ensures that subsequent clustering and sequencing steps do not waste resources on unreachable places.

\textbf{Step 2: Geographic Clustering with Capacity Limits} 
\\ The remaining places are grouped into $K$ clusters (where $K$ is the number of travel days) using the K-Means++ clustering method \cite{arthur2007kmeans}. The objective is to minimize the total geographic spread within each day, which is calculated using the sum of squared distances:
\[
J = \sum_{c=1}^{K} \sum_{p \in C_c} d_{\text{Haversine}}(p, \mu_c)^2
\]
where $C_c$ is the set of places assigned to day $c$, and $\mu_c$ is the centroid of that day's cluster. 

Since clustering only requires relative proximity, it uses the straight-line distance calculated offline via the Haversine formula \cite{sinnott1984haversine} to maintain fast performance:
\[
d_{\text{Haversine}}(i, j) = 2 R \arcsin \left( \sqrt{\sin^2\left(\frac{\Delta \phi}{2}\right) + \cos(\phi_i) \cos(\phi_j) \sin^2\left(\frac{\Delta \lambda}{2}\right)} \right)
\]
where $R$ is the Earth's radius (6371 km). 

After clustering, the system applies two adjustments:
\begin{itemize}
    \item \textbf{Capacity Rebalancing:} Each daily cluster is capped at a maximum of 5 places to keep the schedule realistic. If a cluster exceeds this limit, the place furthest from the centroid is moved, where possible, to the geographically closest cluster that has available capacity.
    \item \textbf{Closed-Day Swapping:} If a place in a cluster is closed on that specific day of the week, the system attempts to swap it to another day's cluster where it is open and where capacity is available.
\end{itemize}

\textbf{Step 3: Distance Matrix Prefetching and Fallbacks}
\\ To sequence the daily routes, the system needs real-world road travel durations instead of straight-line distances. The primary source is the Goong Maps Distance Matrix API. To reduce the number of API calls, for trips with $N \le 24$ places the system prefetches all durations in a single query: from the user's starting point to every place, and between every pair of places. Each entry is the motorbike travel duration in seconds:
\[
t(i, j) = \text{GoongMatrix}(i, j)
\]
When querying travel durations, the system attempts up to three retries with exponential backoff if the Goong API is rate-limited. If the query still fails, it falls back to estimating travel times from the Haversine distance and the average motorbike speed $v_{\text{avg}}$ (30 km/h):
\[
t_{\text{travel}}^{\text{fallback}}(i, j) = \frac{d_{\text{Haversine}}(i, j)}{v_{\text{avg}}} \times 3600
\]

\textbf{Step 4: Route Sequencing and Time Window Checking}
\\ For each day, the system orders the places to solve the Travelling Salesman Problem with Time Windows (TSPTW) \cite{solomon1987tsptw}. Because Step 2 caps each day at a small number of places, the planner can afford an exact search: for a day with up to eight places it evaluates every possible visit order (at most $8! = 40{,}320$, computed in under a millisecond) and keeps the order that schedules the most places, breaking ties with the transition cost defined below. The real travel time from the traveler's starting location to the first stop is included in this search, so the chosen order stays feasible once the GPS times are applied in Step~5.

For the rare day with more than eight places, a Greedy Nearest Neighbor (GNN) heuristic is used as a fallback. It starts at the place closest to the traveler's starting location and then repeatedly selects the next stop that minimizes a transition cost. In both methods, the transition cost penalizes travel time over waiting time to keep the route compact:
\[
\text{Cost}(i, j) = t_{\text{travel}}(i, j) \times 2 + t_{\text{wait}}(j)
\]
where $t_{\text{travel}}(i, j)$ is the motorbike travel time in seconds, and $t_{\text{wait}}(j)$ is the time in seconds the traveler waits if they arrive before place $j$ opens. 

During sequencing, the system tracks the arrival time, wait time, and departure time at each stop. The arrival time $T_{\text{arrive}}(j)$ at a stop includes travel time and a 10-minute parking and entry buffer. If a visit would overlap the lunch break (defaulting to 11:00--13:00), it is shifted to start after lunch. The wait time is defined as:
\[
t_{\text{wait}}(j) = \max(0, T_{\text{open}}(j) - T_{\text{arrive}}(j))
\]
and the departure time at place $j$ is calculated as:
\[
T_{\text{depart}}(j) = \max(T_{\text{arrive}}(j), T_{\text{open}}(j)) + t_{\text{visit}}(j)
\]
A stop is scheduled only if its visit finishes before both its own closing time and the daily end time; otherwise, it is dropped and handled in Step~5. The planner also reports the remaining free time at the end of each day (calculated as the difference between the daily end time and the last departure time) so users can see if more stops can be added.

\textbf{Step 5: GPS Cascade and Conflict Resolution}
\\ Once the initial sequence is created, the system performs two validation steps:
\begin{itemize}
    \item \textbf{GPS Coordinate Cascade:} The actual travel time from the user's starting location to the first stop is injected. This shifts the arrival and departure times of all subsequent stops. If a stop violates the closing time or daily end time, it is dropped from the schedule. The travel time between its predecessor and successor is then recomputed, and the time shifts are cascaded down the remaining stops.
    \item \textbf{Gap Insertion:} Any places dropped during the clustering, sequencing, or cascade phases are passed to a conflict resolution stage. The system attempts to insert these dropped places back into "gaps" (between scheduled stops) of any day where the place is open, provided it fits within its time window and does not make subsequent stops infeasible. This stage reuses the cached Goong matrix from Step~3, so re-inserted places use the same real road durations as the rest of the route instead of straight-line estimates.
\end{itemize}

\textbf{Step 6: Final Route Ordering}
\\ The gap insertion in Step~5 can add a place back into a day after its order was set, so the exact search from Step~4 is applied once more to each day's final set of places to confirm the best visit order. The re-ordered day replaces the previous one only if it still fits every stop after the GPS cascade, so this step can only keep or improve a day and never drops a place that was already scheduled. For a day with more than eight places, the greedy sequence is reused instead.

\subsection{Group Chat}

The Group Chat module enables real-time communication between approved activity members. The system uses a WebSocket gateway to manage connections, message delivery, and user presence.

\textbf{Real-Time Gateway and Presence Management}
\\ Members communicate through a NestJS WebSocket gateway under the \texttt{group-chat} namespace. When a client connects, the gateway verifies the JWT token from the handshake before any messaging is allowed. The client then emits a \texttt{join\_activity} event, and only after the gateway confirms the user is an approved member does it place the client into a dedicated room named \texttt{activity\_\{activityId\}}. Online presence and typing indicators are tracked using two in-memory hash maps (\texttt{onlineMap} and \texttt{typingMap}), with a 3-second auto-stop for typing. Redis is configured in the environment for future scaling, but the current implementation runs on a single server. \\

\textbf{Message Persistence and Offline Dispatch}
\\ When a message is sent, the backend saves it to PostgreSQL and broadcasts it to the room at the same time. Messages and emoji reactions are stored in the \texttt{Message} and \texttt{MessageReaction} tables, keeping all chat data in one database. After broadcasting, the server checks which approved members are not currently in the room and creates a database notification for each of them, with a short summary of the message (for example, a text preview or a note that an image or file was sent). This process is shown in Figure~\ref{fig:chat_pipeline}. \\

\textbf{File Attachments and Read Tracking}
\\ Besides plain text, the module also supports image and file attachments. Each message has a \texttt{type} field (\texttt{TEXT}, \texttt{IMAGE}, or \texttt{FILE}), and attachment messages additionally store the \texttt{mediaUrl}, \texttt{fileName}, and \texttt{fileSize}. The files themselves are uploaded through a separate REST endpoint and saved to Supabase Storage, with a local-disk fallback when the storage service is not configured.

To show unread message counts, the system keeps a \texttt{MessageReadStatus} record for each user and activity that stores the last read time. When a user opens a room, the gateway returns the recent messages together with an unread count computed from messages created after that time, excluding the user's own messages. A \texttt{mark\_read} event then updates the last read time when the user views the room.

\subsection{Moderation System}

The moderation system supports community safety by allowing tourists to report guideline violations and providing administrators with tools to review those reports and act on users or group activities.

Tourists report a group activity or user profile by selecting a violation type (such as spam, scam, or hate speech) and writing a brief description; the report is created with a \texttt{PENDING} status. From a dedicated dashboard, administrators review pending reports and either dismiss a report (marking it \texttt{DISMISSED} with no further action) or resolve it (marking it \texttt{RESOLVED} and optionally hiding the reported activity by setting its status to \texttt{CANCELLED}, or deleting it). Administrators can also suspend user accounts directly.

On the backend, when an administrator decides to suspend an account, the controller triggers the \texttt{banUser} method in \texttt{AdminService}. The database operation runs inside a transaction block to update the user status, increment the token version, create a resolved report, and log the action. On the frontend, the admin panel is built with Next.js using dynamic routing for detailed report views and dashboard widgets. Admin views include statistical breakdowns of violations, user search tables with action buttons, and moderation queues with status badges.

Each moderation action runs inside a Prisma transaction, so the related writes either all succeed or all roll back, avoiding partial updates. Every action, including suspending or restoring a user, resolving or dismissing a report, and cancelling or deleting an activity, is recorded in the \texttt{AdminLog} table to provide an audit trail. Role-based access control (RBAC) via the \texttt{RolesGuard} decorator restricts moderation endpoints to users with the \texttt{ADMIN} role, and JWT token versioning revokes a suspended user's access instantly without a stateful token blacklist.

A key limitation of the current moderation system is its reliance on manual reports by users rather than automated content filtering. Future enhancements will explore integrating natural language processing to automatically flag inappropriate content before it is published.

\section{Database Design}

The database is built on PostgreSQL with the PostGIS extension, which adds support for geographic objects and enables proximity queries such as \texttt{ST\_DWithin} for finding nearby places and activities. The schema is defined and managed using Prisma ORM, which provides type safety and generates the matching SQL migrations when the schema changes. One trade-off is that a single-node database is sufficient for the current scope, but a larger deployment would require spatial index tuning or distributed replicas to handle heavier traffic.

The complete schema contains 15 application tables, illustrated in Figure~\ref{fig:db_complete}, and is organized into three functional clusters: identity and system administration; places and trip planning; and activity and group chat. Each cluster is described below alongside a diagram of the tables it contains.

\subsection{Identity and System Administration}

This cluster handles user accounts, administrative records, and in-app notifications. It contains four tables.

\begin{itemize}
    \item \textbf{users}: \\
    The central table. Stores credentials (\texttt{password\_hash}), profile fields (\texttt{username}, \texttt{full\_name}, \texttt{nationality}, \texttt{languages}), role (\texttt{USER}/\texttt{ADMIN}), and account status (\texttt{ACTIVE}, \texttt{PENDING}, \texttt{BANNED}). The \texttt{token\_version} field invalidates existing JWT tokens when the account is banned or the password is reset. The \texttt{otp\_code} and \texttt{otp\_expires\_at} fields support email verification during registration.

    \item \textbf{reports}: \\
    Records user complaints. The \texttt{entity\_type} and \texttt{entity\_id} fields allow a single table to reference any reportable object. An admin resolves each report by setting \texttt{status} to \texttt{RESOLVED} or \texttt{DISMISSED}.

    \item \textbf{admin\_logs}: \\
    A permanent audit trail of every administrative action. Each row links an admin (\texttt{admin\_id}) to an action string and an optional \texttt{target\_id}. No delete operation is exposed through the API.

    \item \textbf{notifications}: \\
    Stores in-app alerts after key events such as join approvals (\texttt{ACTIVITY\_APPROVED}) or new messages (\texttt{NEW\_MESSAGE}). The \texttt{entity\_type}/\texttt{entity\_id} pair links the notification to the relevant page. Two indexes on \texttt{(user\_id, is\_read)} and \texttt{(user\_id, created\_at)} support unread counts and ordered history.
\end{itemize}

\subsection{Places and Trip Planning}

This cluster stores geographic landmark data and the structured output of the trip planner. It contains five tables and is the most spatially focused part of the schema.

\begin{itemize}
    \item \textbf{places}: \\
    Each row is a tourist landmark. The \texttt{location} column stores a PostGIS \texttt{geometry(Point, 4326)} value with a GiST index, enabling \texttt{ST\_DWithin} proximity queries. Opening hours (\texttt{open\_days}, \texttt{open\_time\_start}, \texttt{open\_time\_end}) are stored separately so the planner can check time-window feasibility during sequencing.

    \item \textbf{place\_gallery}: \\
    Stores extra image URLs for a place. Kept separate from \texttt{places} to avoid widening the main row and to allow cascade deletion.

    \item \textbf{trips}: \\
    One trip per user with a fixed \texttt{num\_days} value. The \texttt{cloned\_from\_id} self-reference records which original trip a clone was copied from, supporting the shared trips feed.

    \item \textbf{trip\_days}: \\
    One row per day of a trip. The \texttt{district} field stores the dominant area for that day, derived from the clustering step.

    \item \textbf{trip\_stops}: \\
    One place visit within a day. The \texttt{stop\_order}, \texttt{arrive\_at}, and \texttt{depart\_at} fields are set by the sequencing algorithm. The \texttt{distance\_from\_prev\_m} and \texttt{duration\_from\_prev\_s} fields cache routing data from Goong Maps so the frontend can display travel times without an extra API call.
\end{itemize}

\subsection{Activity and Group Chat}

This cluster manages the social layer of HanoiGO: user-created meetup events and in-activity group messaging. It contains six tables.

\begin{itemize}
    \item \textbf{activities}: \\
    Represents a meetup event. Stores a PostGIS \texttt{location} column with a GiST index for \texttt{ST\_DWithin} queries. The \texttt{status} field (\texttt{OPEN}, \texttt{CLOSED}, \texttt{CANCELLED}) controls feed visibility; animated marker states are computed on the client from \texttt{scheduled\_at}. A composite index on \texttt{(status, scheduled\_at)} supports the common query for upcoming open activities.

    \item \textbf{activity\_members}: \\
    Join table with a \texttt{status} field (\texttt{PENDING}, \texttt{APPROVED}, \texttt{REJECTED}). The composite primary key on \texttt{(activity\_id, user\_id)} prevents duplicate membership records.

    \item \textbf{activity\_likes}: \\
    Records which users saved an activity. Uses the same composite primary key pattern. The \texttt{saves\_count} on \texttt{activities} is a denormalized counter updated in the same transaction to avoid count queries on the feed.

    \item \textbf{messages}: \\
    Stores chat history. The \texttt{type} field distinguishes \texttt{TEXT}, \texttt{IMAGE}, \texttt{FILE}, and \texttt{SYSTEM} messages. A composite index on \texttt{(activity\_id, created\_at)} supports paginated loading.

    \item \textbf{message\_reactions}: \\
    Stores emoji reactions. The unique constraint on \texttt{(message\_id, user\_id, emoji)} prevents duplicate reactions per user.

    \item \textbf{message\_read\_status}: \\
    Tracks the last time each user read a chat. The \textbf{last\_read\_at} timestamp is compared against the latest message to derive the unread count shown in the navigation badge.
\end{itemize}

\section{Results}

This section lists the modules that were built and are working in the final HanoiGO application. Each item describes what the module delivers for the user. The matching user interfaces are collected in the Appendices, from Figure~\ref{fig:login_ui} to Figure~\ref{fig:admin_dashboard_ui}, so the main text stays focused on the delivered functions rather than on screenshots.

\begin{itemize}
    \item \textbf{User and Security:} Tourists register with email-based OTP verification, log in with a JWT stored in an HttpOnly cookie, and reset a forgotten password by email. Access is separated by role (USER and ADMIN) through the \texttt{RolesGuard}, and banning a user increments the \texttt{token\_version} to invalidate active sessions.

    \item \textbf{Places Discovery:} Tourists browse Hanoi heritage landmarks on a Leaflet map, filter them, and add places to a travel basket. Nearby places are resolved at the database level with PostGIS \texttt{ST\_DWithin} proximity queries, and each place keeps its parsed opening hours for later scheduling.

    \item \textbf{Trip Planner:} From the selected places and trip settings, the system generates a timed multi-day itinerary using K-Means++ day grouping and an exact time-window ordering, with a greedy fallback for larger days and Goong Maps travel times. The result is shown in a two-panel interface with a day-tab timeline and a route map, and can be saved to the user's profile (Figure~\ref{fig:trip_planner_ui}).

    \item \textbf{Activity and Group Chat:} Tourists host or join group activities and browse shared trips in a card-based experiences feed (Figure~\ref{fig:experiences_feed_ui}), and approved members talk in a real-time Socket.io group chat with typing indicators, emoji reactions, file attachments, and unread tracking (Figure~\ref{fig:group_chat_ui}).

    \item \textbf{Admin and Moderation:} Administrators use a dashboard with summary cards and Recharts statistics (Figure~\ref{fig:admin_dashboard_ui}) and manage users, places, activities, and user reports, with every action recorded in an audit log.
\end{itemize}


\section{Discussion}

This section evaluates the two parts of the system whose quality can be measured with concrete numbers: the trip planner and the real-time group chat. For the planner, the goal is to check whether the automated planner produces more useful daily itineraries than the simple methods a tourist would otherwise use by hand; for the chat, the goal is to confirm that the server-side message path is sufficiently fast to avoid being a bottleneck for real-time delivery.

\subsection{Trip Planner Effectiveness}

The planner takes a set of places and trip settings and returns a timed daily schedule:

\begin{center}
\fbox{\parbox{0.92\textwidth}{
\textbf{Input:} selected places, number of days, daily start and end time, lunch break, and the traveler's start point. \\
\textbf{Output:} for each day, an ordered list of stops with arrival and departure times; any place that cannot fit its opening hours is returned as unscheduled.
}}
\end{center}

To test its usefulness, the planner output was compared against two manual strategies a tourist might use instead:

\begin{itemize}
    \item \textbf{HanoiGO:} the full pipeline of Chapter~\ref{ch:methodology} (K-Means++ day grouping and exact time-window ordering).
    \item \textbf{By-District:} places grouped by administrative district and visited in the order they were defined in the input dataset.
    \item \textbf{Random:} places assigned to days and ordered at random, averaged over 200 seeds.
\end{itemize}

All three methods used the same inputs and the same feasibility check (\texttt{calculateVisitWindow}), with travel times retrieved from a frozen Goong motorbike distance matrix to ensure the difference in outcomes comes only from the planning strategy. The HanoiGO arm runs the production \texttt{TripPlannerService}. Table~\ref{tab:planner_results} reports four metrics on four scenarios, and Figure~\ref{fig:planner_gantt} draws the Case~1 schedules on a timeline. Here, compactness measures the average of the mean distances from each scheduled stop in a day to the day's geographic centroid, indicating geographic concentration.

In Case~1, the Mausoleum closes at 10:30 and a nearby museum at noon, while the other places stay open all day. As Figure~\ref{fig:planner_gantt} shows, By-District reaches the Mausoleum after it closes and drops it, and the random order drops about one and a half places on average; the planner visits the early-closing places first and schedules all five, with travel time marginally higher than By-District only because it fits one extra place. This trap also drove a design change: an earlier greedy version looked one step ahead and stranded the Mausoleum, so small days now use the exact time-window search of Chapter~\ref{ch:methodology}, which checks every order.

In Case~2, a three-day trip across several districts, the planner and By-District both schedule all twelve places while the random order drops about two. The planner's advantage here is geographic concentration: its days are about four times more compact (0.35 against 1.53, Table~\ref{tab:planner_results}), since administrative districts do not always follow the road network. It also keeps the lowest total travel time (100 minutes against 112 and 136), though the margin over By-District is small once real road durations are used.

Case~3 places the first day of a two-day trip on a Monday, when three of the eight selected places are closed. The planner reads each place's opening days and moves the three closed places to the second day, scheduling all eight; By-District ignores the weekday and drops the three left on Monday (5/8), while the random order drops about two (6.3/8). By-District shows tighter compactness (0.36 against 0.61) only because it visits fewer places; the planner trades slight compactness for fitting every place selected.

Case~4 adds an afternoon-only venue, a water puppet theatre opening at 15:00, to four morning places. The planner schedules the theatre last and fills the morning with the others, so it never waits (0 minutes); By-District and Random keep the theatre in its given position and idle until it opens, building up 404 and 257 minutes of waiting, which also forces By-District to drop two places (3/5). Ordering by opening time, rather than by district or at random, is what avoids the wasted wait.

The Goong durations are a frozen snapshot and all methods share the same inputs, so the comparison stays consistent across runs.

\subsection{Real-Time Chat Performance}

The group chat uses Socket.io rather than HTTP polling so members see new messages without refreshing the page. To check that delivery is fast enough for real-time use, the round-trip latency of a message was measured end to end against the running \texttt{GroupChatGateway}. A real Socket.io client joins a room and sends a message; since the sender is also in the room, it receives its own broadcast, which lets a single client time the full path of one message:

\begin{center}
\fbox{\parbox{0.92\textwidth}{
\texttt{send\_message} (client) $\rightarrow$ gateway handler $\rightarrow$ \texttt{Prisma} insert into PostgreSQL $\rightarrow$ \texttt{server.to(room).emit} $\rightarrow$ \texttt{new\_message} (client)
}}
\end{center}

The test sent 200 messages back to back (after a 20-message warm-up) and recorded the time from each \texttt{send\_message} call to the matching \texttt{new\_message} event. The handshake that opens the connection, including the JWT check in \texttt{handleConnection}, was timed separately. Every message created during the run was deleted afterwards so the database was left unchanged. Table~\ref{tab:chat_latency} reports the results.

The median round-trip stayed near 5~ms and the 95th percentile under 7~ms. These figures were recorded locally on a single system over the loopback interface, where the application server and PostgreSQL ran on the same host, so no real network cost was present. Two costs the loopback setup omits would appear in a distributed deployment: the network round-trip between the user and the server, and the network hop to the database host.

What the numbers do show is that the gateway's own compute (the membership check, message serialisation, and Socket.io fan-out) is not the bottleneck; in production, the dominant latency terms would be those two network paths. The test also used a small two-member room, so it does not capture how fan-out cost grows with more participants. Presence and typing state are tracked in in-memory maps (\texttt{onlineMap} and \texttt{typingMap}) on a single server, so horizontal scaling would require the Redis adapter noted in Chapter~\ref{ch:conclusion}.

\section{Conclusion}

This thesis presented HanoiGO, a web application that helps foreign tourists in Hanoi plan multi-day trips and connect with other travelers on a shared map. The five implemented modules (user authentication, places discovery, trip planning, activity management with group chat, and administrative moderation) address the objectives set out in Chapter~I.

The trip planner, the central technical contribution, uses K-Means++ clustering and an exact time-window search to build timed daily schedules. Compared with two simpler ordering strategies, it scheduled more places and reduced total travel time, particularly when some places have early closing times. The Socket.io group chat gateway achieved a median round-trip of 5.1~ms locally on a single system, confirming that the server's own processing is not a bottleneck for real-time delivery.

The platform has known limitations in its current form, and several directions for future improvement are identified in the sections that follow.

\section{Limitations}

The current implementation has four limitations. The trip planner requires users to fill in all parameters manually before a schedule can be generated, including trip duration, daily start and end times, visit durations, and start location. Travel times are based on a motorbike profile only, using the Goong Maps API or a fixed 30~km/h fallback that does not adjust for traffic conditions or peak hours. Presence and typing state in the group chat are kept in in-memory maps (\texttt{onlineMap} and \texttt{typingMap}) on a single server, so the chat cannot scale horizontally without a distributed message broker. Finally, the evaluation used simulated scenarios and objective metrics only; no study with real tourists was conducted, so how practical the application is in everyday use has not been confirmed.

\section{Future Work}

First, a conversational AI assistant using the Gemini model will be added so that users can set up a trip through a natural chat instead of filling in a form. The existing manual settings form will remain available for users who prefer it.

Second, multi-modal routing options such as walking and public transit will be explored to complement the current motorbike-only travel time calculations.

Third, the landmark dataset will be extended to cover other major cities in Vietnam so the platform can support trips outside Hanoi.

Fourth, the group chat and notification gateways will be scaled horizontally using a Redis Pub/Sub adapter to support multiple concurrent server instances.

Fifth, a usability study with real foreign tourists will be conducted to confirm whether the trip planner and activity features work well in practice, and to guide further improvements to the interface.
